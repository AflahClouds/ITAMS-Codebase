## Clouds post-implementation living-spec overlay

This overlay intentionally changes upstream Spec Kit v1.0.6 living-spec mutation timing while retaining its schemas and artifact roles. For every update, use a temporary upstream-shaped change feature directory during Specify and Clarify; never edit the canonical living spec before implemented behavior is verified. Clarify always coverage-scans and asks only material questions. Keep business goal, users, behavior, rules, terms, scope, exclusions, examples, calculations, boundaries, reconciliation, failures, permissions, risk, acceptance, and relevant prior decisions in the closest upstream artifact; never store secrets, credentials, unnecessary PII, raw production data, or transcripts.

New or convention-free Clouds projects default to this overlay. An existing project with a different established persistence convention requires designated-owner approval before migration; this repository's migration is already expressly approved.

A **sprint** is the full local AFK path after approved Clarify: Plan, risk-justified quality work, Tasks, Analyze, implementation, separate builder/reviewer delivery, verification, Converge, and guide-owned closeout. Before sprint approval, native Specify and authorized setup may write the temporary specification/checklist, Clarify answers, feature metadata, development-branch state, and initial constitution under its own governance; dependent Plan, Tasks, and code changes may not start. Present the Specify result and built-in checklist in business language and pause until the user explicitly approves entering Clarify. After the Clarify coverage scan and checklist revalidation, present the clarified design and pause until the user explicitly approves entering the final scope decision. These two design-stage approvals are required even when the user earlier requested or preauthorized a sprint. Only after both, present the final clarified scope and ask for scope acceptance and current-update local-sprint authority; bind any valid earlier explicit full-sprint authority to the unchanged approved scope, current temporary `spec.md`, checklist, repository/ref/revision identity without a duplicate authority question. A generic implementation request, earlier update's authority, scope-only answer, stale/changed identity, attachment, or silence never grants standing sprint authority. For a validated accepted-scope Chat handoff without AFK authority, seek only the missing exact bound local authority unless a design-stage or final-scope approval is unverified or a material conflict/change returns to its owning stage. Sprint authority grants no external mutation, push, promotion, release, or publication.

Stop before dependent mutation for required user information; scope, behavior, or technology conflict; unsafe sensitive-data handling; uncertain destructive action; missing external authority; stale or changed authorization identity/handoff; unavailable required capability or inability to preserve user work; unrecoverable blocker; or the workflow safety limit. Assess is conditional on genuine problem/value uncertainty; extra checklists are risk-based; Bug is used only when installed and enabled or after separately authorized installation, otherwise use the normal temporary living-change route.

The guide independently selects one builder and one fresh read-only reviewer using purpose, risk, ambiguity, oracle completeness, repair cost, availability, and user input, and records why no cheaper available choice meets each quality bar. They may use the same model but are separate assignments, invocations, and permissions. Astra is explicit-user-only; no paid API, purchased capacity, or reset redemption is allowed. For high-risk deterministic work, require business-owned expected outcomes, fail-before tests, targeted and relevant broader checks, and permanent regression protection for every corrected defect.

If included workspace usage blocks a required delegated builder or reviewer role, preserve the worktree, pause safely, wait for the allowance or gate to reset, and resume that same delegated builder/task with its existing process/session handle. Do not silently substitute the guide or primary agent, consume reset credits, or use paid capacity; a changed workflow requires separate user authorization.

A delegated builder that starts a long-running test or program retains its process/session handle, records or learns the expected wait, and polls that same run only when the result can change the next action. Do not launch a duplicate or claim a truncated run passed. If its turn ends first, resume that same delegated builder/task with its existing process/session handle to finish polling and verification; the guide or primary agent may coordinate but must not execute builder-owned verification.

### GitHub repository ownership
